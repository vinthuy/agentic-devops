## 1. 背景与问题

开发者和小团队有大量“定义清楚但占用时间”的工程任务：修一个已知 bug、加一个小功能、补单元测试、更新文档、升级依赖。这些任务的特点是：需求可以用一两段话描述，验收可以通过测试判断，但手工做一遍需要上下文切换和反复调试。

现有的 AI 编码 Agent（GitHub Copilot coding agent、Devin、Codex Cloud、Jules、Claude Code Action 等）已经能“从 Issue 生成 PR”，但普遍存在以下问题：

1. **PR 质量不稳定**：需要多轮人工返工，用户把它当“草稿”而非“可合并的结果”。
2. **验证不充分**：没有跑完整测试或只做了表面检查，就声称“已完成”。
3. **成本不可预测**：按配额、ACU 或 Token 计费，任务前无法估算，任务后难以归因。
4. **需求模糊时方向跑偏**：Agent 不会主动确认理解，直接开工。
5. **安全与合规顾虑**：代码、密钥和内网访问权限要交给外部平台，很多团队不接受。
6. **多工具割裂**：同时使用多个 Agent，缺少统一的任务、成本和审计视图。

**本产品要解决的核心问题**：让用户用一句需求触发一条自动化流水线，系统在受控环境中完成编码与验证，并以一个**可审查、可追溯、有成本记录**的 Pull Request 交付到远程 GitHub 仓库。

---

## 2. 产品定位

**一句话定位**：一个自托管的“需求到 PR”自动化工程流水线，以**验证闭环、成本透明和过程审计**为核心差异。

**与竞品的关系**：
- 不与 Copilot、Codex 等在“能否开 PR”上竞争。
- 我们把它们（以及 Claude API）视为可插拔的执行后端，自己负责任务分级、需求确认、验证闭环、预算护栏和审计。

## 3. 目标与非目标

### 3.1 目标（当前单机版本）

| 编号 | 目标 | 衡量方式 |
|---|---|---|
| G1 | 用户提交一条 S 级需求后，系统自动完成编码、验证，并推送分支、开 PR | 端到端成功率 ≥ 60%（在 S 级任务基准集上） |
| G2 | 每个 PR 都附带可验证的验收结果、成本与运行日志 | PR 描述模板完整率 100% |
| G3 | 预算上限清晰，模型调用执行中实时记账，超预算自动熔断 | 预算超限的任务中，实际花费 ≤ 上限 × 1.1；任务前历史成本预测暂不作为当前能力 |
| G4 | 所有运行步骤可追溯，支持中断后恢复 | 任意中断任务可通过 `resume` 继续，无数据丢失 |
| G5 | 默认安全：Agent 不能直接推送 `main`，不能访问受保护文件 | 安全策略测试用例通过率 100% |

### 3.2 非目标（当前版本不做）

- 不做自动合并 PR（人工合并是唯一路径）
- 不支持 GitLab、Bitbucket 等非 GitHub 平台
- 不做多租户 SaaS 与复杂计费
- 不支持 L 级（大型、跨模块、需要架构决策）任务的全自动执行
- 不做 Web 管理后台（MVP 仅 CLI + 生成的 Markdown 报告）
- 不做 IDE 插件
- Docker 容器不是本地开发前置条件；默认使用受限本地进程执行。Docker 仅作为可选的更强隔离后端。

## 4. 用户与场景

### 4.1 目标用户

| 角色 | 描述 | 核心诉求 |
|---|---|---|
| **个人开发者 / 技术负责人（主要用户）** | 管理 1–5 个仓库，希望把琐碎任务交给自动化 | 省时间、不失控、知道花了多少钱 |
| **小团队工程师（次要用户）** | 团队共享一套流水线，任务由多人提交 | 统一的任务视图、可审查的 PR、清晰的边界 |
| **安全 / 合规负责人（间接用户）** | 关心代码与密钥是否外泄，操作是否可审计 | 自托管、权限最小化、审计日志 |

### 4.2 核心场景

- **S1 修复 Bug**：用户提交“登录页在邮箱含 `+` 号时校验失败，复现步骤见 Issue #123”，系统生成修复、补测试并开 PR。
- **S2 小功能**：用户提交“为 `/api/users` 增加 `role` 过滤参数，并更新 OpenAPI 文档”。
- **S3 补测试**：用户提交“为 `utils/date.py` 补充边界用例，覆盖率提升到 90%”。
- **S4 需求不清晰**：用户提交模糊需求，系统在计划阶段提出 2 个澄清问题，用户回复后再继续。
- **S5 任务失败**：验证反复不通过，系统在预算或次数上限前停止，生成失败报告并转人工。

## 5. 功能需求

优先级定义：**P0** 必须有（MVP 阻塞项）；**P1** 应该有（MVP 后尽快）；**P2** 可以有（远期）。

### 5.1 任务提交与分级

| ID | 需求 | 优先级 |
|---|---|---|
| FR-001 | 支持通过 CLI 提交任务，输入包括目标仓库、需求文本（或文件）、可选的 Issue 编号 | P0 |
| FR-002 | 支持通过已认证的 `gh` CLI 从 GitHub Issue 导入标题与正文；Issue 正文视为不可信输入。不导入评论、不关闭 Issue。回写评论只按 FR-047 与 FR-073 发生，不在导入路径上顺手回写 | P1 |
| FR-003 | 任务创建后，系统自动分级为 S / M / L；用户可手动覆盖 | P0 |
| FR-004 | MVP 仅执行 S 级任务；M 级进入等待审批；L 级不得直接进入编码。没有通过校验的拆分时，父任务进入 `NEEDS_HUMAN` 并说明拆分失败 | P0 |
| FR-066 | L 级由规划拆成多段 M 级子任务，每段单独停在审批门。批准一段不会批准下一段。拆分失败时父任务进入 `NEEDS_HUMAN`，不编码 | P1 |
| FR-005 | 分级依据：涉及文件数、预估改动行数、是否涉及配置/CI/依赖/数据库迁移等敏感区域 | P0 |

### 5.2 需求理解与计划

| ID | 需求 | 优先级 |
|---|---|---|
| FR-010 | Planner 输出结构化计划，包括：改动文件列表、实施步骤、**机器可校验的验收标准**、预估成本 | P0 |
| FR-011 | 验收标准必须映射到可执行的检查（测试用例名、命令、退出码），不接受纯主观描述 | P0 |
| FR-012 | 需求含糊时，Planner 可输出澄清问题，任务进入 `NEEDS_INFO` 状态，等待用户回复 | P1 |
| FR-013 | 计划生成后，S 级任务可自动执行；M 级必须由用户通过 `approve` 命令确认 | P0 |
| FR-014 | 用户可在审批时修改计划（编辑验收标准或限定文件范围） | P1 |
| FR-067 | 规划前可对仓库做有界只读检索（受路径策略约束，不能写、不能跑任意命令）。检索结果不足以支撑需求时停在 `NEEDS_INFO`，不得猜 | P1 |
| FR-069 | 仓库根目录的 `AGENTS.md` 作为本地指令注入规划与审查。它不能放宽禁止路径、命令策略或预算 | P1 |

### 5.3 编码与执行

| ID | 需求 | 优先级 |
|---|---|---|
| FR-020 | 每个任务在独立的 git worktree 中执行，基于目标仓库的默认分支创建 | P0 |
| FR-021 | Coder 通过工具（读文件、写文件、搜索、执行命令）完成修改，所有工具调用可记录 | P0 |
| FR-022 | 执行命令必须经过命令策略检查（白名单 + 黑名单）；追加参数不得引入执行类标志（如 `-exec`、`-c`），违规命令被拒绝并记录 | P0 |
| FR-023 | 命令经策略检查后在任务 worktree 中执行；本地受限进程是默认且可独立工作的执行方式，Docker 是可选强化隔离，不得成为运行前置条件 | P0 |
| FR-024 | 每个任务验证通过后生成包含任务 ID 的提交；验证/Reviewer/CI 修复在同一任务分支与 PR 上迭代 | P0 |
| FR-025 | 编码器可调用 `request_info` 请求具体澄清问题；任务进入 `NEEDS_INFO`，用户回复后返回规划，不允许借此扩大策略允许范围 | P1 |

### 5.4 验证与修复闭环

| ID | 需求 | 优先级 |
|---|---|---|
| FR-030 | 每个仓库在 `repos.yaml` 中配置验证命令（lint、test、build），顺序执行 | P0 |
| FR-031 | 按计划中的验收标准逐项检查，并输出通过/失败矩阵 | P0 |
| FR-032 | 验证失败时，将失败日志（截断后）回传 Coder 进行修复，形成循环 | P0 |
| FR-033 | 修复循环有上限：最多 N 次（默认 3），超限进入 `NEEDS_HUMAN` | P0 |
| FR-034 | 独立 Reviewer 审查 diff、需求、计划与验收证据；只因需求未满足、正确性、安全或验证被削弱等具体问题打回，风格意见不得阻塞；结果经程序校验 | P1 |
| FR-035 | 不允许 Agent 修改验证配置或删除/跳过测试以使验证通过；此类改动需检测并拦截 | P0 |

### 5.5 GitHub 交付

| ID | 需求 | 优先级 |
|---|---|---|
| FR-040 | 分支命名：`agent/<task-id>-<slug>`，推送到远程，不直接推送默认分支 | P0 |
| FR-041 | 通过 `gh` CLI 幂等创建或更新 PR：同一分支已有 PR 时更新标题/正文，不重复创建 | P0 |
| FR-042 | PR 正文包含：需求原文、计划摘要、改动摘要、验收结果矩阵、成本、任务 ID、运行日志路径 | P0 |
| FR-043 | PR 默认标记为 Draft（可配置为 Ready for Review） | P0 |
| FR-044 | 若任务来自 Issue，PR 正文注明 Issue URL；当前不自动关闭 Issue 或发表评论 | P1 |
| FR-045 | 推送前执行密钥扫描，发现疑似密钥则阻止推送并转人工 | P0 |
| FR-046 | `ci_watch` 显式开启时监听 PR 检查；通过后完成，无 CI 时明确记录，失败日志回传修复至配置上限，超时/查询失败转人工 | P1 |
| FR-047 | 任务完成后，在 Issue 下回写一条评论，包含 PR 链接与任务摘要 | P2 |
| FR-073 | 协作者在来源 Issue 上用 `/approve`、`/reject`、`/replan` 评论驱动现有审批命令。评论正文其余部分不进入模型。重复投递同一条评论不得重复转移状态 | P1 |
| FR-074 | 独立审查的结论要写到草稿 PR 的 review 上：打回对应请求修改，通过对应评论。GitHub 写入失败不回滚已经做出的状态转移 | P1 |

### 5.6 成本与预算

| ID | 需求 | 优先级 |
|---|---|---|
| FR-050 | 每次模型调用记录 Token 数与费用（依据配置的单价表计算） | P0 |
| FR-051 | 任务创建时展示预算上限；模型用量按 triage/planner/coder/reviewer 角色实时记账。基于历史数据的任务前成本预测暂不承诺 | P2 |
| FR-052 | 每个任务与每个仓库可设置预算上限，超限时熔断并转 `NEEDS_HUMAN` | P0 |
| FR-053 | 提供单任务明细与全局成本看板，按角色/模型聚合并列出高花费任务。`cost report --repo` 与 `--day` 按仓库和账本 UTC 日期筛选 | P1 |

### 5.7 任务管理与可观测性

| ID | 需求 | 优先级 |
|---|---|---|
| FR-060 | CLI 命令：`task create / list / status / logs / approve / reply / cancel / resume` | P0 |
| FR-061 | 每个状态转换与关键事件写入事件表，可按任务查询完整时间线 | P0 |
| FR-062 | 每个任务生成本地运行报告（Markdown），包含完整事件时间线与成本明细 | P0 |
| FR-063 | 支持任务中断后 `resume`，从最后一个成功的状态继续 | P0 |
| FR-064 | 支持同时运行的任务数上限（默认 2），其余排队 | P1 |
| FR-065 | `agentdev webhook` 校验 GitHub 签名后，把带 `agent-ready` 的 Issue 入队，并把 `/approve`、`/reject`、`/replan` 交给现有审批。标签不批准、不进入编码。进程内定时轮询仍未做，审批超时由外部 cron 调 `sweep` | P2 |
| FR-075 | `agentdev sweep` 处理已到期的审批和锁，不启动新任务，也不在进程内常驻。调度交给外部 cron | P1 |

### 5.8 配置与策略

| ID | 需求 | 优先级 |
|---|---|---|
| FR-070 | `repos.yaml` 定义每个仓库的：默认分支、验证命令、允许的命令、受保护路径、预算上限 | P0 |
| FR-071 | `policy.yaml` 定义全局策略：禁止命令、禁止路径、修复/审查上限与超时；网络出站隔离由宿主环境负责，当前不声称由应用层强制 | P0 |
| FR-072 | 模型与单价配置独立于代码（`models.yaml`），可切换模型提供方 | P0 |
| FR-068 | `models.yaml` 可按 triage / planner / coder / reviewer 指定不同模型。未指定的角色用默认模型。被用到的模型必须有单价，否则按缺单价告警，不得记成免费 | P1 |

## 6. 非功能需求

| 类别 | 需求 |
|---|---|
| **安全** | GitHub 操作由已认证 `gh` CLI 执行；模型 key 仅从环境变量读取；敏感路径不可读写；推送前扫描疑似密钥；Issue 内容视为不可信输入 |
| **安全（提示注入）** | Issue 正文、命令输出、CI 日志用明确的不可信边界包裹；命令受白名单/黑名单与工作目录约束；本地进程模式不是 OS 级沙箱 |
| **可靠性** | 状态持久化，进程崩溃后可恢复；外部调用（模型、GitHub）带重试与退避；幂等的推送与 PR 创建 |
| **成本** | 单任务默认预算上限 $2，可配置；所有模型调用可计费追溯 |
| **可观测性** | 结构化日志（JSON Lines）；每个任务有独立的日志目录与运行报告 |
| **可维护性** | 模型客户端、Coder backend、Planner、Reviewer、CodeHost、CIWatcher 通过 Go 接口解耦；提示词版本化并嵌入二进制 |
| **可用性** | CLI 输出清晰，错误信息包含下一步建议；常用命令有示例 |
| **兼容性** | Go 单二进制；依赖 Git 与（交付/Issue/CI 时）已认证的 `gh` CLI。当前主要在 Windows 开发，Linux 支持仍需独立验证 |
| **性能** | 单个 S 级任务的端到端耗时目标 ≤ 15 分钟（不含人工等待时间） |
| **可部署性** | 单机运行，无需 Docker 或外部数据库；任务数据存于本地 SQLite。Docker 仅为可选隔离增强 |

## 7. 任务分级规则（S / M / L）

| 等级 | 典型特征 | 执行策略 |
|---|---|---|
| **S** | 改动 ≤ 3 个文件且 ≤ 200 行；不涉及敏感区域；验收标准可由现有测试或新增测试覆盖 | 自动执行，无需审批 |
| **M** | 改动 4–10 个文件或 200–800 行；或涉及依赖、配置、接口变更 | 计划生成后需用户 `approve` |
| **L** | 改动 > 10 个文件或 > 800 行；跨模块重构；涉及数据库迁移、认证授权、CI 流水线 | 拆成按顺序单独审批的 M 级子任务。父任务不编码。拆不开则待人工。批准一段不会批准下一段 |

**敏感区域（一律至少提升为 M 级）**：`.github/workflows/`、依赖清单（`package.json`、`go.mod`、`requirements*.txt` 等）、数据库迁移目录、认证相关模块、部署与基础设施配置。

> 分级是启发式的，由 Planner 估算后由规则引擎做最终判定。规则引擎的优先级高于模型的判断。

## 8. 任务状态与用户流程

### 8.1 主流程

```
用户提交需求
   │
   ▼
[TRIAGING] 分级 ───── L ──▶ 拆成 M 级子任务；拆不开则 [NEEDS_HUMAN]
   │
   ▼
[PLANNING] 生成计划
   │
   ├── 需求模糊 ──▶ [NEEDS_INFO] ──用户回复──▶ 回到 PLANNING
   │
   ├── M 级 ──▶ [AWAITING_APPROVAL] ──用户 approve──▶
   │
   ▼
[CODING] ◀──────────────────┐
   │                        │ 失败（未超限）
   ▼                        │
[VERIFYING] ────────────────┤
   │ 通过                   │
   ▼                        │
[REVIEWING] ────────────────┘
   │ 通过
   ▼
[COMMITTING] → [PUSHED] → [PR_OPENED] ──ci_watch=false──▶ [DONE]
                                       └─ci_watch=true──▶ [CI_WATCHING] → [DONE]
                                │ CI 失败（未超限）
                                └──▶ 回到 CODING

任意状态：超限 / 超预算 / 异常 ──▶ [NEEDS_HUMAN]
用户取消 ──▶ [CANCELLED]
```

### 8.2 用户交互点

| 交互点 | 用户动作 | 命令 |
|---|---|---|
| 提交需求 | 输入需求与仓库 | `agentdev task create` |
| 澄清问题 | 回复系统的问题 | `agentdev task reply <id>` |
| 计划审批（M 级） | 确认或修改计划 | `agentdev task approve <id>` |
| 人工介入 | 查看原因，决定修复或放弃 | `agentdev task status / logs`，然后 `resume` 或 `cancel` |
| 最终审查 | 复核 Reviewer 结果与 Draft PR，再人工决定是否合并 | GitHub 界面 |

## 9. 用户故事与验收标准

### US-01 提交 S 级修复任务
**作为**技术负责人，**我希望**提交一段 Bug 描述后，系统自动产出可审查的 PR，**以便**我只需做 Review 而不用亲自编码。

- AC1：`agentdev task create --repo acme/app --text "..."` 返回任务 ID
- AC2：任务在无人值守情况下进入 `DONE`，且 GitHub 上存在对应的 Draft PR
- AC3：PR 正文包含验收结果矩阵、成本和运行报告路径
- AC4：分支名符合 `agent/<task-id>-<slug>` 格式

### US-02 需求澄清
**作为**用户，**我希望**系统在需求不清时先问我，**以便**避免做错方向。

- AC1：Planner 输出澄清问题时，任务状态为 `NEEDS_INFO`，且 CLI 可查看问题
- AC2：`reply` 之后任务重新进入 `PLANNING`
- AC3：未回复期间不产生编码相关的模型成本

### US-03 M 级审批
**作为**用户，**我希望**中等规模的改动在执行前先经过我确认，**以便**控制风险。

- AC1：M 级任务计划生成后状态为 `AWAITING_APPROVAL`，未审批不执行编码
- AC2：审批后按计划执行；审批时可修改验收标准
- AC3：计划中的文件范围与实际改动不一致时，任务转 `NEEDS_HUMAN`

### US-04 预算熔断
**作为**用户，**我希望**设定预算上限，**以便**避免意外的高额费用。

- AC1：单任务默认预算为 $2，可通过配置修改
- AC2：达到预算 80% 时记录警告事件，达到 100% 时立即停止调用模型
- AC3：熔断后任务进入 `NEEDS_HUMAN`，保留已完成的工作（分支中的 commit）

### US-05 验证不可绕过
**作为**安全负责人，**我希望**Agent 无法通过删除测试或修改验证配置来“通过”任务。

- AC1：若 diff 修改了 `repos.yaml` 中定义的验证命令相关文件，或删除/跳过了测试用例，验证失败并转 `NEEDS_HUMAN`
- AC2：被拦截的操作记录在事件表中，报告中可见

### US-06 中断恢复
**作为**用户，**我希望**机器重启或进程崩溃后，任务能继续，**以便**不丢失进度。

- AC1：进程被杀死后，`agentdev task resume <id>` 从最后一个已完成的状态继续
- AC2：恢复后不会重复推送或重复创建 PR（幂等）

### US-07 密钥保护
**作为**用户，**我希望**即使 Agent 误写了密钥，也不会推送到远程。

- AC1：推送前扫描检测到疑似密钥时，阻止推送，任务转 `NEEDS_HUMAN`
- AC2：`.env` 与 `*.pem` 等路径不可被 Agent 读取或修改

## 10. 成功指标

| 类别 | 指标 | 目标/状态 | 说明 |
|---|---|---|---|
| 结果质量 | S 级任务端到端成功率（PR 创建且验证全部通过） | ≥ 60% | 基于 20 个标准任务的基准集 |
| 结果质量 | 首次 CI 通过率 | ≥ 50%（待测） | 仅统计已开 PR 的任务；当前未在真实目标仓库基准集测量 |
| 效率 | 平均修复轮数 | ≤ 2 | 验证失败到通过之间的循环次数 |
| 成本 | 单个 S 级任务平均成本 | ≤ $0.5 | 以当期模型单价计算 |
| 成本 | 预算超限的任务中，超支比例 | ≤ 10% | 验证熔断机制有效 |
| 安全 | 安全策略测试通过率 | 100% | 包括禁止推送默认分支、禁止访问敏感路径 |
| 体验 | 人工介入率（转 NEEDS_HUMAN 的比例） | ≤ 30% | 反映 S 级分级是否合理 |

**基准集**：MVP 开始前，准备 20 个 S 级任务（包括 bug 修复、小功能、补测试、文档更新），分布在 2–3 个不同技术栈的小型仓库中，作为回归测试。

## 11. 发布计划

| 阶段 | 范围 | 退出标准 |
|---|---|---|
| **M0：原型** | CLI 提交需求 → 本地 worktree 中 Coder 修改 → 手动运行验证 → 输出 diff | 能完成 3 个 S 级任务的本地修改 |
| **M1：MVP** | Go 单机流水线；分级/规划/编码/验证；审批、澄清、成本熔断；密钥扫描、分支推送与 Draft PR；恢复 | 自动化测试通过；基准集成功率仍需正式测量 |
| **M2：增强** | 独立 Reviewer；可选 CI 监听与修复；幂等 PR 更新；Issue 标题/正文导入；成本看板；`request_info` | 自动化测试通过；真实 GitHub CI 首次通过率 ≥50% 尚待测量。Docker 为可选增强，不是阶段阻塞项 |
| **M3：控制面（当前代码；版本常量仍是 0.13.0）** | 标签只表示接入；Issue 完成回写与评论审批；审查意见写回 PR；`webhook`；`sweep`；规划前只读检索；按角色选模型；`AGENTS.md`；L 级拆成逐段审批的 M 级子任务；CI 差异基准；成本报表按仓库与日期筛选 | 上述行为有自动化测试。评论、标签和 Webhook 不能绕过策略与审批门。进程内定时器未做 |

## 12. 风险与缓解

| 风险 | 影响 | 可能性 | 缓解措施 |
|---|---|---|---|
| 模型生成的代码质量不达标 | 成功率低，用户失去信任 | 高 | 验证闭环 + 小范围分级 + Draft PR 默认 |
| 验收标准由模型自己写，容易“自证通过” | 验证形同虚设 | 高 | 验收标准需映射到现有或新增测试；禁止修改验证配置；Reviewer 独立审查 |
| 提示注入（恶意 Issue 诱导执行危险命令） | 数据泄露或仓库被破坏 | 中 | 命令白名单；Issue 内容不可信标记；网络出站限制；敏感操作审批 |
| 成本失控 | 费用超预期 | 中 | 预算熔断 + 实时记账 |
| 平台方推出同类功能 | 差异化削弱 | 高 | 聚焦治理、成本透明、自托管；把平台能力作为执行后端接入 |
| 本地进程不是操作系统级隔离 | 高风险任务可能需要更强边界 | 中 | 默认限制 worktree、命令、路径、超时与权限；需要更强隔离时可选 Docker，不可用时本地开发仍可运行 |
| 任务分级不准确 | 本应审批的任务被自动执行 | 中 | 规则引擎覆盖敏感区域；分级结果可人工覆盖；记录分级偏差用于调优 |

## 14. 术语表

| 术语 | 含义 |
|---|---|
| 任务（Task） | 一次需求提交及其完整生命周期 |
| 分级（Triage） | 根据规模与风险将任务归为 S / M / L |
| 计划（Plan） | Planner 输出的结构化实施方案，包括文件范围与验收标准 |
| 验收标准（Acceptance Criteria） | 可被程序检查的完成条件，映射到具体测试或命令 |
| 工作区（Workspace） | 任务专用的 git worktree |
| 验证（Verify） | 运行 lint、测试、构建等命令并比对验收标准 |
| 熔断（Circuit Breaker） | 超过预算或次数上限时强制停止，转人工 |
| 执行后端（Execution Backend） | 负责实际编码的 Agent 实现，如 Claude API 直连，或未来的 Claude Code、Codex |
